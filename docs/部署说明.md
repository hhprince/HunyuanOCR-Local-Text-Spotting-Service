# 部署说明（昇腾 NPU 多卡）

> 本文描述把本项目部署到**昇腾多卡集群**的完整步骤，以及开发机和生产机必须
> 保持一致的地方。接口和参数见 [../使用说明.md](../使用说明.md)，
> 需求见 [../需求文档.md](../需求文档.md)。

## 1. 目标环境

生产环境按 **8× Ascend 910B-64G**（单卡 64GB HBM，HCCS 互联）设计，
CPU 为 64 核 ARM64（aarch64）。选型依据：

| 部件 | 配置 | 对方案的影响 |
|---|---|---|
| NPU | 8× Ascend 910B-64G | **没有 NVIDIA 卡**。必须 torch_npu + CANN，CUDA 代码路径全部不可用 |
| CPU | 64 核 ARM64 | **aarch64 架构**，x86_64 的 venv 完全不能复用，要新建环境 |
| 内存 | 数百 GB | 绰绰有余 |
| 磁盘 | NVMe | 放模型权重和图片 |

**8 卡用数据并行，不用张量并行。** 模型只有 1.12B 参数，fp16 权重 2.24GB，
单卡 64GB 装得下还剩 60GB。张量并行要拉起 HCCL 通信组，延迟和故障面都大得多，
收益却是负的。

## 2. 架构

```
HTTP 进程（uvicorn，1 个）          ← 只做协议解析和转发，不占算力
  └── 8 个 worker 进程               ← 每进程 1 张 NPU + 1 份模型
        req_q[i] / resp_q[i]         ← 每个 worker 一对私有队列
```

请求进来 → 挑一个空闲 worker → 投进它的队列 → 从它的队列取结果。
每个 worker 同时只处理一张图，8 张卡 = 8 路并发，worker 之间零通信。

用**私有队列**而不是一条大队列，是为了避免并发时取错别人的响应：
每个 worker 一次只处理一个请求，响应和请求一一对应。

## 3. 环境安装

### 3.1 CANN 与 torch_npu

三者必须配套，**照昇腾官方版本配套表装，不要自己拼**：
CANN 版本 ↔ torch_npu 版本 ↔ torch 版本。表在昇腾社区
（hiascend.com → 社区 → Ascend PyTorch 适配）。

约束只有一个：torch 要 ≥ 2.1（模型官方要求 PyTorch 2.1+）。

```bash
# CANN 用昇腾官网的离线包安装（不是 pip），装完 source 环境变量
source /usr/local/Ascend/ascend-toolkit/set_env.sh

pip install torch==2.4.0
pip install torch-npu==2.4.0            # aarch64 轮子在 PyPI 上有
pip install -r requirements.txt
```

### 3.2 transformers 版本（最大的不确定项）

- 模型的 `config.json` 里写的是 `transformers_version: 5.15.0.dev0`
- 官方归档文档里原生 transformers 路径用的是 `5.13.0`（正式版）
- 5.13.0 未必包含 `hunyuan_vl` 架构（它是在 5.x 开发期才加进去的）

**做法**：先装 5.13.0，装不上或加载不了就钉 `5.21.0.dev0`（nightly 也是纯 Python
轮子，aarch64 装得没问题，只是没有 CI 保障）。用哪个都行，**但必须用验收流程
确认结果没变**（第 7 节）。

快速验证能不能加载：

```bash
python -c "
from transformers import AutoModelForImageTextToText
m = AutoModelForImageTextToText.from_pretrained('tencent/HunyuanOCR', dtype='float16')
print('ok', type(m).__name__)"
```

### 3.3 权重

HF 缓存是**平台无关**的（safetensors 就是文件），可以从 x86_64 机器直接拷：

```
~/.cache/huggingface/hub/models--tencent--HunyuanOCR/  →  服务器同路径
```

拷完设 `HF_HUB_OFFLINE=1` 断网跑。也可以直接下载（国内加 `HF_ENDPOINT=https://hf-mirror.com`）。

`--model` 参数既可以填仓库名（`tencent/HunyuanOCR`），也可以填本地目录绝对路径。

### 3.4 跑起来

```bash
cd /opt/ocr
export HF_HOME=/data/models/hf
export HF_HUB_OFFLINE=1
source /usr/local/Ascend/ascend-toolkit/set_env.sh

python serve_ocr_prod.py --host 0.0.0.0 --port 8000 --model tencent/HunyuanOCR
```

默认只监听 127.0.0.1（避免误暴露），对外服务**必须显式** `--host 0.0.0.0`。
`--npu-ids 0,1,2,3,4,5,6,7` 决定用哪几张卡，默认就是这 8 张。

建议挂 systemd：

```ini
[Service]
WorkingDirectory=/opt/ocr
ExecStart=/opt/ocr/.venv/bin/python serve_ocr_prod.py --host 0.0.0.0 --port 8000
Environment=HF_HOME=/data/models/hf
Environment=HF_HUB_OFFLINE=1
Environment=ASCEND_RT_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
Restart=always
```

> `ASCEND_RT_VISIBLE_DEVICES` 是给 CANN 运行时看的设备白名单，和
> `CUDA_VISIBLE_DEVICES` 一个角色。不设的话进程能看到全部 8 张卡。

## 4. 生产和开发必须一致的部分

| 项 | 值 | 理由 |
|---|---|---|
| 提示词 | 官方 `spotting_json`，一字不改 | 换自造提示词后回归集上少找出多个真实块 |
| dtype | `float16` | 官方默认 bf16 尾数只有 7 位；fp16 与 fp32 实测等价 |
| 采样 | greedy，**不加** `repetition_penalty=1.08` | 那个惩罚是为长文档防重复退化用的，本场景同短语重复出现是正常内容，加了实测掉真块、造假块 |
| attn | `sdpa` | eager 物化完整注意力矩阵，输出与 sdpa 逐字相同但更费显存。**昇腾上如果 sdpa 不可用就改 `--attn eager`**，64GB 显存扛得住 |
| scale | 1.5（默认值） | 见第 5 节，**必须在自己的数据上测** |
| max_new_tokens | 2048 | 输出 700~1500 字符（约 400~500 token），有三倍余量 |
| 进程优先级 | 不设置 | 生产机独占，不该跟同机其它租户抢；开发机则必须提（见第 8 节） |

**这些参数住在 `ocr_core.py` 里，两边共用同一份代码**，所以不会出现"生产上
提示词和开发机不一样"这种事。

## 5. 放大倍数的硬约束

processor 的 `max_pixels = 2048×2048 = 4.19MP`（`preprocessor_config.json`）。

以 1166×784（0.91MP）的图为例：

| scale | 放大后 | 实际进模型 | 结果 |
|---|---|---|---|
| 1.0 | 1166×784 | 1166×784 | 视觉 token 少，细小的字可能读不出 |
| **1.5** | **1749×1176（2.06MP）** | **1736×1176** | 默认值 |
| 2.14 | 临界点 | 开始触发内部缩放 | — |
| 2.5 | 2915×1960（5.71MP） | 2492×1652 | **更差**：先 LANCZOS 放大再被内部降采样，双重重采样把笔画糊掉 |

**显存大不是调大 scale 的通行证**，瓶颈在重采样不在显存。

但 1.5 也**不是**放之四海皆准的最优值——见 [实验记录.md](实验记录.md) 里两组
看起来矛盾的数据。**结论：必须用 `tools/score.py` 在自己的数据上测。**

## 6. 性能（未实测，务必实测替换）

单卡每次只喂一张图，是**发射/带宽瓶颈而不是算力瓶颈**，所以不能按 NPU 和
消费级显卡的算力差几十倍去估。合理预期是**每卡 2~6 秒/张**，8 卡并行的吞吐
就是单卡的 8 倍。这个数必须实测替换，别拿它当承诺。

想再提吞吐只有两条路，都需要重新验证准确度：

1. **多图一次推理**（连续批处理）——要改 left padding，padding 会影响数值，
   得重新跑验收；
2. 换 vLLM-ascend —— 但它换不来准确度（官方明确 "accuracy alignment verified"），
   只是工程复杂度上升，而且 `hunyuan_vl` 未必在 vllm-ascend 的模型注册表里。

## 7. 上线验收清单

**必须做完再切流量。** 核心是第 1 步：

```bash
# 1. 用生产代码把回归集跑一遍，产出和开发机同构的 JSON
python serve_ocr_prod.py --batch --input-dir /data/regression --output-dir /data/ocr_out
```

```bash
# 2. 和开发机基准逐字符比
python tools/compare_runs.py /data/ocr_out/*.json 开发机基准.json --diff
```

判定标准和完整清单见 [准确度验收.md](准确度验收.md)。

其余检查项：

- [ ] `GET /health` 返回 `ready_workers: 8`，8 个 worker 的 `alive` 都是 true
- [ ] 各 worker 的 `device` 是 8 个不同的 NPU（用 `npu-smi info` 核对）
- [ ] 8 路并发请求都返回 200，`words_result` 不为空
- [ ] 连续跑 1000 张，显存不涨（`npu-smi info` 看进程显存）、worker 不掉
- [ ] 服务重启后能正常拉起（模型加载可能要 1 分钟）
- [ ] 单个 worker 挂掉时，其余 worker 仍能服务
      （当前实现是请求超时返回 503，**不会自动重启该 worker**——
      靠 systemd 的 `Restart=always` 或 supervisor 兜底）

## 8. 风险清单

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-1 | 昇腾算子实现与 CUDA 不完全一致 | 结果与开发机有细微差异 | 上线前跑验收流程量化 |
| R-2 | transformers 版本与架构不匹配 | 加载失败 | 锁版本，先跑加载验证 |
| R-3 | torch_npu 上的 sdpa 未覆盖 | 报错或算子回退到 CPU（很慢但不崩） | 报错就改 `--attn eager` |
| R-4 | CANN / torch_npu / torch 版本不配套 | import 报错 | 照官方配套表装 |
| R-5 | 模型输出偶发格式错误 | 该图结果为空 | `ocr_core.parse_words` 已有兜底（见第 9 节） |
| R-6 | 主机侧 CPU 被抢占导致推理变慢 | 吞吐严重下降 | 生产机独占一般不会遇到；真遇到了查进程优先级 |

## 9. 两个踩过的坑

### 9.1 输出解析：不能让一个坏元素毁掉整张图

模型偶尔会吐出格式错误的元素，实测见过：

```json
{"box755, 880, 818, 903], "text": "000000"}
```

`'"box": ['` 少了冒号和左方括号。整段输出因此不是合法 JSON。

**原来的实现直接返回"解析失败"，整张图的所有块全丢**——不是丢 1 个，是全丢。
在合成样例上实测 6 张里有 4 张中招。

修法分两层（见 `ocr_core.parse_words`）：

1. 整段按 JSON 解析（正常路径）；
2. 失败则退化成"从原文里逐个抠出 `text` 字段"，不依赖 JSON 结构。

顺带一个坑：这种坏输出里的**引号数是奇数**，任何靠引号/括号配对切数组的做法
都会错位——包括原来那个 `rfind("]")`（它会命中 box 坐标里的 `]` 把数组截断）。

### 9.2 multiprocessing spawn：调 `start()` 的脚本必须有 main guard

Windows 和 Linux 上 `multiprocessing` 的 spawn 方式，子进程会**重新导入主模块**。
如果主模块在 import 层面就调了 `pool.start()`，子进程导入时又去 spawn 一次，
抛：

```
RuntimeError: An attempt has been made to start a new process before the
current process has finished its bootstrapping phase.
```

**这个报错发生在子进程里，父进程只看到 worker 死了**（`exitcode=1`），
表现是"所有请求卡到超时"——很容易误判成 GPU 或队列的问题。

正确写法：所有会 spawn 的逻辑都放进 `if __name__ == "__main__":`。
`serve_ocr_prod.py` 本身是对的；`test_service.py` 也是对的（都放在 guard 里）。
